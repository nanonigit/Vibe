# ジャンル英語統一・ナレッジ設計

## 調査根拠

- [Lazywebのジャンルブラウズレポート](https://www.lazyweb.com/report/lazyweb/aabeca7b-6874-4f37-80d2-712b44209c61/?source=create)では、音楽ブラウズ一覧は簡潔に保ち、AllMusic型のジャンルページでは歴史や特徴を詳細領域へ分離しています。
- 現在のSwiftUI画面にも、一覧の1行説明と選択ジャンルの詳細ヘッダーがあります。各行を過密にせず、この階層を強化します。
- MediaWiki公式REST APIはページ検索と言語間リンクを提供します。日本語ページから対応する英語タイトルを取得し、日英両方の出典付き概要を取得します。

## 根本原因

`GenreNormalizer.normalize` は、静的置換後にも日本語が残る場合、安全のため元の表記を返します。一方、バックグラウンド処理は未解決件数を記録せず、完了時に進捗を消します。そのため、日本語が残ったまま「自動整理はオン」と表示され、動作していないように見えます。

## データモデル

スキーマ移行v12で `genre_knowledge` を追加します。

- `raw_key`: 大文字・小文字を無視する検索キー、主キー
- `raw_genre`: 元の表記
- `canonical_name`: 英語正規名
- `summary_ja`, `summary_en`: 出典付き概要
- `source_title`, `source_url`: 出典情報
- `resolved_at`: キャッシュ日時

曲数ではなく一意なジャンル別名数に比例する小さなテーブルです。

## 解決フロー

1. 内蔵正規化を適用する。
2. 結果に日本語がなければ直ちに利用する。
3. 元表記キーで `genre_knowledge` を検索する。
4. 元表記に音楽文脈を加えて日本語Wikipediaを検索する。
5. 音楽関連候補と英語言語リンクを必須とする。
6. 英語ページタイトルを英語正規名へ整形する。
7. 日英の概要と出典URLを保存する。
8. 既存のファイル書き込みまたは保留編集経路で正規名を適用する。
9. 曖昧・通信失敗時は元表記を保持し、未解決件数を増やす。

## UI

- ジャンル一覧: 英語正規名、保存済みの1行概要、曲数。
- 選択ジャンル: 詳細概要と `Wikipedia` 出典リンク。未取得時は内蔵説明へフォールバックする。
- 管理画面: 実行中は確認・更新・未解決件数を表示し、完了後も直近結果と日時を保持する。

## 安全性とプライバシー

- Wikipediaへ送るのはジャンル名だけとし、曲名、パス、APIキー、音声は送信しない。
- テストでは本番DBを書き換えない。
- ID3v2.2の確認・修復規則とオフライン保留編集を維持する。
- 成功して出典を示せる結果だけを保存し、曖昧な結果は未解決のままにする。

## Lazywebの反映

一覧は2行以内に保ち、出典と長い内容は選択ジャンル詳細へ置く段階的開示を採用します。また、長時間処理には単なる有効表示ではなく、状態が分かる明示的な文言を使います。
